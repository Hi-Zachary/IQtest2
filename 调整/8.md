# V11.1 / V12 改进方案：先验证实验可比性，再进行部分共享

## 1. 当前问题

当前 V11 的目标是通过任务完全隔离，消除 Quality 与 Alignment 的梯度冲突：

```text
Quality:
LoRA-Q -> DG-MPQ -> Quality Fusion -> Q Head

Alignment:
LoRA-A -> MSCM -> Alignment Fusion -> A Head
```

当前 split4 结果：

| Model | Q-SRCC | A-SRCC |
|---|---:|---:|
| R0 | 0.8574 | 0.6710 |
| B1 = R0 + DG-MPQ | **0.8625** | 0.6672 |
| B2 = R0 + MSCM | 0.8560 | **0.7154** |
| Full = R0 + DG-MPQ + MSCM | 0.8481 | 0.7024 |

表面上 Full 同时弱于 B1 和 B2。但在 V11 的硬隔离结构下，如果初始化、数据顺序和随机过程完全一致，理论上应该有：

```text
Full 的 Quality 分支 ≈ B1 的 Quality 分支
Full 的 Alignment 分支 ≈ B2 的 Alignment 分支
```

因为：

```text
L_Q 只能更新 Quality 分支参数
L_A 只能更新 Alignment 分支参数
```

因此，当前 Full 明显变弱，首先应该排查实验控制变量，而不是继续堆新模块。

---

## 2. 当前最可能的问题：消融之间没有真正做到 matched initialization

虽然训练代码固定了随机种子：

```python
random.seed(seed)
np.random.seed(seed)
torch.manual_seed(seed)
```

但当前模型的参数初始化顺序仍然会因为模块开关不同而变化。

例如：

```text
Backbone
↓
Quality Projection / Fusion / Head
↓
DG-MPQ（仅 use_dg_mpq=True 时实例化）
↓
Alignment Projection / Fusion / Head
↓
MSCM（仅 use_mscm=True 时实例化）
```

于是：

```text
B2:
不实例化 DG-MPQ
→ 直接初始化 Alignment 分支

Full:
先实例化 DG-MPQ
→ 消耗一批 PyTorch RNG
→ 再初始化 Alignment 分支
```

所以即便都使用 `seed=42`，B2 与 Full 的 Alignment 分支也不一定拥有相同初始权重。

对于 AGIQA-3K 这种小规模数据集，这种初始化差异足以造成明显性能波动。

此外，Dropout 也会造成不同消融之间随机轨迹不一致：Full 每个 batch 比 B1/B2 额外执行模块，因此 RNG 消耗顺序不同，后续 Dropout mask 也会变化。

因此目前这组 V11 结果还不足以证明 Full 结构本身有问题。

---

# 3. 第一阶段：V11.1 严格控制实验

## 3.1 目标

V11.1 不追求提升性能，只验证：

> 当初始化、模型参数布局和随机过程尽量一致时，Full 的对应分支能否复现单独消融的性能。

如果仍然不能复现，就应该继续排查隐藏耦合或实现问题。

---

## 3.2 所有消融始终实例化完整模型

不要再根据开关决定是否实例化 DG-MPQ / MSCM。

当前类似：

```python
if use_dg_mpq:
    self.dg_mpq = DgMpq(...)
else:
    self.dg_mpq = None

if use_mscm:
    self.mscm = MSCM(...)
else:
    self.mscm = None
```

改为始终：

```python
self.dg_mpq = DgMpq(...)
self.mscm = MSCM(...)
```

四组实验全部实例化：

```text
LoRA-Q
LoRA-A
DG-MPQ
MSCM
Quality Visual Projection
Quality Text Projection
Quality Fusion
Quality Head
Alignment Visual Projection
Alignment Text Projection
Alignment Fusion
Alignment Head
```

模块开关只控制 forward 中是否使用，而不改变参数初始化顺序。

---

## 3.3 固定 Alignment Fusion 输入维度

如果当前 `use_mscm=False` 时 Alignment Fusion 使用：

```text
[v_a, t_a]
```

而开启 MSCM 时使用：

```text
[v_a, t_a, a_corr]
```

那么 B1 与 Full 的 Alignment Fusion 本身就是不同网络。

V11.1 统一固定：

```text
Alignment Fusion: 3D -> D
```

关闭 MSCM：

```python
a_corr = torch.zeros_like(t_a)

h_a = self.alignment_fusion(
    torch.cat([v_a, t_a, a_corr], dim=-1)
)
```

开启 MSCM：

```python
a_corr = self.mscm(...)

h_a = self.alignment_fusion(
    torch.cat([v_a, t_a, a_corr], dim=-1)
)
```

这样不同消融的基础网络参数布局保持一致。

---

## 3.4 四组实验加载同一份初始化权重

不要只依赖 seed，直接保存一份完整模型初始化：

```python
torch.manual_seed(42)

model = MSQRNetV11(...)
torch.save(
    model.state_dict(),
    "v11_1_init_seed42.pth"
)
```

所有实验统一：

```python
model = MSQRNetV11(...)

model.load_state_dict(
    torch.load("v11_1_init_seed42.pth"),
    strict=True
)
```

这样可以保证同名参数初始值完全一致。

---

## 3.5 控制实验阶段关闭 Dropout

V11.1 建议：

```text
drop = 0
```

这不是最终设计决策，只是为了验证结构。

否则即使初始参数一致，不同消融因为 forward 路径不同，仍会消耗不同数量的 RNG，导致后续 Dropout mask 不一致。

## R0

```text
Dual LoRA
+ independent Q/A projections
+ independent Q/A fusion
+ independent heads
```

但：

```text
DG-MPQ disabled
MSCM disabled
```

---

## B1

```text
R0 + DG-MPQ
```

Quality：

```text
LoRA-Q
-> multi-level visual features
-> DG-MPQ
-> enhanced quality representation
-> Q Fusion
-> Q Head
```

Alignment 与 R0 完全一致。

---

## B2

```text
R0 + MSCM
```

Alignment：

```text
LoRA-A
-> H9/H12/global visual features
-> MSCM
-> cross-modal correspondence feature

```

Quality 与 R0 完全一致。

---

## Full

```text
R0
+ DG-MPQ
+ MSCM
```

但两条任务分支仍然完全隔离。

# 5. V11.1 最关键的 sanity check

重点不是最终 best score，而是逐 epoch 曲线。

应该观察：

```text
B1 Quality curve
≈
Full Quality curve
```

以及：

```text
B2 Alignment curve
≈
Full Alignment curve
```

定义：

$$
\Delta_Q(e)
=
\operatorname{SRCC}_{Full,Q}(e)
-
\operatorname{SRCC}_{B1,Q}(e)
$$

$$
\Delta_A(e)
=
\operatorname{SRCC}_{Full,A}(e)
-
\operatorname{SRCC}_{B2,A}(e)
$$

如果硬隔离实现正确，应该有：

$$
|\Delta_Q(e)| \approx 0
$$

$$
|\Delta_A(e)| \approx 0
$$

至少不应该长期出现 $0.01$ 量级的系统差异。

---

# 6. V11.1 判定标准

## 情况 A：B1-Q ≈ Full-Q，B2-A ≈ Full-A

说明：

```text
V11 的结构隔离是正确的
此前 Full 弱主要受初始化/随机轨迹影响
```

此时再进入 V12，研究“完全隔离是否损失跨任务正迁移”。

## 情况 B：仍然明显不一致

例如：

```text
B1 Q-SRCC = 0.862
Full Q-SRCC = 0.850
```

即便已经：

```text
same initialization
dropout = 0
same split
same seed
same optimizer
```

仍有明显差距，则停止结构迭代，继续排查：

```text
1. 是否仍有共享可训练参数；
2. optimizer param groups 是否一致；
3. scheduler 是否一致；
4. loss 是否真的按任务独立反向传播；
5. 两条 LoRA 是否存在共享对象；
6. 是否仍有 stochastic op；
7. forward 中是否存在 inplace 修改；
8. dataloader 顺序是否一致；
9. AMP / numerical randomness；
10. checkpoint reload 是否一致。
```

# 7. 第二阶段：V12 部分共享

如果 V11.1 验证通过，则进入 V12。

核心思想：

> 共享基础适配，隔离任务专属建模。

不再使用完全独立的：

```text
LoRA-Q
LoRA-A
```

而改回：

```text
Shared Visual LoRA
```

但 DG-MPQ 与 MSCM 仍然严格属于各自任务。

---

# 8. 为什么重新共享 LoRA

当前一个值得重视的现象是：

```text
V10 B2 / MSCM:
A-SRCC ≈ 0.743

V11 B2 / MSCM:
A-SRCC ≈ 0.715
```

具体数值还需要最终统一协议验证，但趋势说明：

> 当 Alignment 分支失去来自 Quality loss 的共享视觉适配后，性能可能反而下降。

这意味着两个任务之间可能同时存在：

```text
共享底层适配时的 positive transfer
+
任务模块直接耦合时的 negative transfer
```

因此问题未必是“要不要共享”，而更可能是：

> 共享发生在哪一层。

---

# 9. V12 推荐结构

```text
                         Frozen CLIP
                             │
                      Shared Visual LoRA
                             │
               ┌─────────────┴─────────────┐
               │                           │
           Quality                     Alignment
               │                           │
            DG-MPQ                       MSCM
               │                           │
              v_q                        a_corr
               │                           │
       Quality Fusion             Alignment Fusion
               │                           │
        Quality Head              Alignment Head
               │                           │
               Q                           A
```

梯度关系：

```text
Shared Visual LoRA:
接受 L_Q + L_A

DG-MPQ:
只接受 L_Q

MSCM:
只接受 L_A

Quality projection/fusion/head:
只接受 L_Q

Alignment projection/fusion/head:
只接受 L_A
```

---

# 10. V12 Quality 分支

```text
image
↓
Frozen CLIP + Shared LoRA
↓
H3 / H6 / H9 / H12
↓
DG-MPQ
↓
delta_q
↓
v_q = v0_q + tanh(lambda_q) * delta_q
↓
[v_q, t_q]
↓
Quality Fusion
↓
Quality Head
↓
Q
```

示意：

```python
feat = backbone.encode_image(x)

v0_q = quality_visual_proj(feat["global_v"])

delta_q = dg_mpq(
    feat["vision_hidden"][3],
    feat["vision_hidden"][6],
    feat["vision_hidden"][9],
    feat["vision_hidden"][12],
)

v_q = v0_q + torch.tanh(lambda_q) * delta_q

h_q = quality_fusion(
    torch.cat([v_q, t_q], dim=-1)
)

q = quality_head(h_q)
```

---

# 11. V12 Alignment 分支

```text
image
↓
Frozen CLIP + Shared LoRA
↓
H9 / H12 / global visual
↓
MSCM
↓
a_corr
↓
[v_a, t_a, a_corr]
↓
Alignment Fusion
↓
Alignment Head
↓
A
```

关键要求：

> Alignment 分支不要使用 DG-MPQ 增强后的 $v_q$。

而应直接从 shared LoRA 后的 CLIP 特征建立自己的路径：

```python
v_a = alignment_visual_proj(
    feat["global_v"]
)

a_corr = mscm(
    feat["vision_hidden"][9][:, 1:, :],
    feat["vision_hidden"][12][:, 1:, :],
    t_a,
    feat["global_v"],
    global_t,
)

h_a = alignment_fusion(
    torch.cat([v_a, t_a, a_corr], dim=-1)
)

a = alignment_head(h_a)
```

这样可以避免 Alignment loss 直接作用于 DG-MPQ。

# 12. 推荐最终消融

| Model | Shared LoRA | DG-MPQ | MSCM |
|---|---:|---:|---:|
| B0 | × | × | × |
| R0 | ✓ | × | × |
| B1 | ✓ | ✓ | × |
| B2 | ✓ | × | ✓ |
| Full | ✓ | ✓ | ✓ |

其中：

```text
LoRA = adaptation infrastructure
DG-MPQ = Contribution 1
MSCM = Contribution 2
```

不要再把 LoRA、fusion、routing 或 loss 包装成新的贡献点。

---

# 13. 对 Full 的合理目标

不需要要求：

```text
Full Q > B1 Q
且
Full A > B2 A
```

同时严格成立。

更合理的结果应是：

```text
B1:
Quality 最强或接近最强

B2:
Alignment 最强或接近最强

Full:
Q 接近 B1
A 接近或超过 B2
Joint 最优
```

例如：

```text
B1:
Q = 0.870
A = 0.710

B2:
Q = 0.860
A = 0.740

Full:
Q = 0.868
A = 0.742
```

这种结果已经足以说明两个模块具有互补性。

---

# 14. 当前不建议加入的机制

现阶段不要加入：

```text
PCGrad
GradNorm
动态 loss weighting
L2 soft sharing
teacher-student / distillation
two-stage training
复杂 routing
额外 consistency loss
更多 prompt bank
更多 cross-attention block
```

原因是目前最基础的问题——Full 的下降究竟来自结构还是实验随机性——还没有被彻底分离。

继续堆机制只会让实验解释更困难。

---

# 15. 推荐执行顺序

## Step 1：实现 V11.1

完成：

```text
所有模块始终实例化
统一 Fusion 参数布局
统一 initialization checkpoint
dropout = 0
```

## Step 2：先只跑 split4

优先：

```text
B1
B2
Full
```

R0 可选。

## Step 3：检查逐 epoch 曲线

重点比较：

```text
B1-Q vs Full-Q
B2-A vs Full-A
```

## Step 4：如果不能重合

停止结构迭代，继续查实现问题。

## Step 5：如果基本重合

实现 V12：

```text
Shared LoRA
+
DG-MPQ Quality-only
+
MSCM Alignment-only
+
Independent projections/fusions/heads
```

## Step 6：V12 首轮仍只跑 split4

重点记录：

$$
\Delta_Q
=
SRCC_{Full,Q}
-
SRCC_{B1,Q}
$$

$$
\Delta_A
=
SRCC_{Full,A}
-
SRCC_{B2,A}
$$

希望：

```text
Delta_Q 接近 0
Delta_A 接近 0 或 > 0
Joint 优于 B1 / B2
```

## Step 7：结构稳定后再跑多 split / 多 seed

最后进行正式稳健性验证：

```text
3~5 个 content-aware split
```

报告：

```text
mean ± std
```

并统一 checkpoint selection 规则。

# 16. 最终结论

当前最重要的问题不是继续设计第三个机制，而是先回答：

> V11 Full 的下降究竟是结构问题，还是初始化和随机轨迹不一致造成的伪差异？

因此下一步首先完成 V11.1 matched-initialization control。

如果 V11.1 验证通过，则 V12 最值得尝试的方向是：

```text
Shared Visual LoRA
+
Quality-specific DG-MPQ
+
Alignment-specific MSCM
+
Independent task heads
```

即：

> **共享基础适配，隔离任务专属建模。**

这个方向既保留 Quality 与 Alignment 之间可能存在的正迁移，又避免 DG-MPQ 与 MSCM 在任务专属层面互相污染，同时保持方法结构简洁、消融清晰，也更适合作为最终论文或保研面试版本。
