# V8 最后一轮改进方案：Task-Oriented Routing

## 1. 当前问题

当前 V8-Slim Final 的整体结构已经比较稳定：

```text
CLIP ViT-B/16
  + Visual LoRA
  + DG-MPQ
  + HCMI-ViT
  + Shared Fusion
  + Dual Regression Heads
```

当前统一 50 epoch 后的结果大致为：

| Model | Q-SRCC | Q-PLCC | A-SRCC | A-PLCC |
|---|---:|---:|---:|---:|
| B1 = LoRA + DG-MPQ | 0.8563 | 0.9153 | 0.7046 | 0.8432 |
| Full = LoRA + DG-MPQ + HCMI | 0.8524 | 0.9127 | 0.7126 | 0.8441 |

可以看到：

```text
Full vs B1

Q-SRCC  -0.0039
Q-PLCC  -0.0026

A-SRCC  +0.0080
A-PLCC  +0.0009
```

因此：

- Full 的双任务综合表现更好；
- Alignment 有明确提升；
- Quality 只有轻微下降；
- 但从消融表展示上看，Full 没有超过 B1 的 Quality，视觉上不够漂亮。

当前已经可以确认：

> 这不是训练 epoch 不统一造成的，而是一个真实但很轻微的 Quality–Alignment trade-off。

---

# 2. 最可能的原因

当前 forward 为：

```python
v = v0 + tanh(lambda_q) * delta_q
c = t0 + tanh(lambda_a) * delta_a

h = shared_fusion(torch.cat([v, c], dim=-1))

q = quality_head(h)
a = align_head(h)
```

也就是说：

```text
DG-MPQ
  ↓
  v
   \
    \
     [v, c]
       ↓
 shared fusion
       ↓
       h
     /   \
    Q     A

HCMI
  ↓
  c
```

虽然：

- DG-MPQ 是 Quality-oriented；
- HCMI 是 Alignment-oriented；

但两个任务最终使用的是同一个：

```text
h = Fusion(v, c)
```

因此 HCMI 修改后的：

```text
c = t0 + λaΔa
```

不仅进入 Alignment Head，也会进入 Quality Head。

这意味着：

> HCMI 在提高图文对齐表示的同时，也会改变 Quality Head 所依赖的输入分布。

因此出现：

```text
Alignment ↑
Quality   ↓ slightly
```

是合理的。

---

# 3. 最终建议：Task-Oriented Routing

不增加任何新模块，也不增加任何参数。

仅修改信息路由方式。

当前：

```python
h = shared_fusion(torch.cat([v, c], dim=-1))

q = quality_head(h)
a = align_head(h)
```

改为：

```python
h_q = shared_fusion(torch.cat([v, t0], dim=-1))
h_a = shared_fusion(torch.cat([v, c], dim=-1))

q = quality_head(h_q)
a = align_head(h_a)
```

其中：

```text
v  = DG-MPQ 增强后的 visual representation
t0 = 原始 CLIP text anchor
c  = HCMI 增强后的 alignment representation
```

---

# 4. 修改后的数据流

最终：

```text
                     CLIP ViT-B/16
                           │
              ┌────────────┴────────────┐
              │                         │
         Vision Encoder            Text Encoder
              │                         │
        Visual LoRA               Frozen Text
              │                         │
              │                        t0
              │                         │
      ┌───────┴────────┐                │
      │                │                │
   DG-MPQ          HCMI-ViT ◄───────────┘
      │                │
      │               Δa
     Δq                │
      │                ▼
      ▼          c = t0 + λaΔa
v = v0 + λqΔq         │
      │                │
      │        ┌───────┘
      │        │
      │        │
      ▼        ▼
   [v, t0]   [v, c]
      │        │
      │        │
      └── shared_fusion
            两次调用
          /           \
         /             \
       h_q             h_a
        │               │
 Quality Head      Alignment Head
```

注意：

```text
shared_fusion
```

仍然只有一套参数。

只是对两种输入分别调用。

因此：

> 参数量完全不增加。

---

# 5. 为什么 Quality 用 [v, t0]

Quality 路径定义为：

```python
h_q = shared_fusion(
    torch.cat([v, t0], dim=-1)
)
```

其中：

```text
v
```

已经包含：

```text
Visual LoRA
+
DG-MPQ
```

提供的视觉质量信息。

而：

```text
t0
```

保留原始 CLIP text global representation。

这样 Quality prediction 仍然是多模态的：

```text
enhanced visual representation
+
original text anchor
```

但不会被：

```text
HCMI alignment residual
```

直接改变。

理论上这最接近 B1 的 Quality pathway。

---

# 6. 为什么 Alignment 继续用 [v, c]

Alignment 路径：

```python
h_a = shared_fusion(
    torch.cat([v, c], dim=-1)
)
```

其中：

```text
v = DG-MPQ enhanced visual representation
c = HCMI enhanced cross-modal representation
```

这里不建议改成：

```python
[v0, c]
```

原因是之前实验已经说明：

DG-MPQ 虽然主要服务 Quality，但同样经常能够提升 Alignment。

因此没有必要人为把 DG-MPQ 从 Alignment path 中移除。

最终逻辑：

```text
DG-MPQ
  ├── Quality
  └── Alignment

HCMI
  └── Alignment
```

---

# 7. 修改后的模块职责

## 7.1 DG-MPQ

定位：

**Quality-oriented visual enhancement**

输入：

```text
L3 / L6 / L9 / L12 ViT patch features
```

输出：

```text
delta_q
```

最终：

```python
v = v0 + tanh(lambda_q) * delta_q
```

作用于：

```text
Quality path
Alignment path
```

---

## 7.2 HCMI-ViT

定位：

**Alignment-oriented hierarchical cross-modal interaction**

输入：

```text
L6 detail visual tokens
L12 semantic visual tokens
generation prompt tokens
```

输出：

```text
delta_a
```

最终：

```python
c = t0 + tanh(lambda_a) * delta_a
```

仅直接作用于：

```text
Alignment path
```

这样模块职责会更加清晰。

---

# 8. model_v8.py 具体修改

当前：

```python
# ===================== shared fusion + dual heads =====================
h = self.heads.shared_fusion(
    torch.cat([v, c], dim=-1)
)

q = self.heads.quality_head(h)
a = self.heads.align_head(h)

self._last_ratios = ratios
return torch.cat([q, a], dim=-1)
```

改成：

```python
# ===================== task-oriented routing =====================

# Quality:
# 使用 DG-MPQ enhanced visual representation，
# 但保持原始 text anchor，避免 HCMI residual 对 Quality path 的干扰。
h_q = self.heads.shared_fusion(
    torch.cat([v, t0], dim=-1)
)

# Alignment:
# 使用 DG-MPQ visual representation + HCMI enhanced alignment representation。
h_a = self.heads.shared_fusion(
    torch.cat([v, c], dim=-1)
)

q = self.heads.quality_head(h_q)
a = self.heads.align_head(h_a)

self._last_ratios = ratios
return torch.cat([q, a], dim=-1)
```

只需要改这一小段。

---

# 9. heads.py 不需要修改

继续保持：

```python
self.shared_fusion = nn.Sequential(
    nn.Linear(dim * 2, dim),
    nn.GELU(),
    nn.Dropout(drop),
)

self.quality_head = nn.Linear(dim, 1)
self.align_head = nn.Linear(dim, 1)
```

不需要新增：

```text
quality_fusion
alignment_fusion
```

所以不会增加参数。

---

# 10. 为什么不采用双 Fusion

另一种方案是：

```python
h_q = quality_fusion([v,c])
h_a = alignment_fusion([v,c])
```

虽然也合理，但会：

```text
新增一套 512 → 256 fusion
```

约增加：

```text
0.13M parameters
```

而且会让结构变成：

```text
shared backbone
+
two modules
+
two task-specific fusion networks
+
two heads
```

复杂度又开始上涨。

相比之下 Task-Oriented Routing：

```text
零新增参数
零新增模块
零新增 loss
零新增超参数
```

更适合当前项目。

---

# 11. 为什么这个修改不是“为了刷表硬改”

这个修改和模块设计本身是一致的。

原本就定义：

```text
DG-MPQ = Quality-oriented
HCMI   = Alignment-oriented
```

因此：

```text
Quality 不直接使用 HCMI residual
```

在逻辑上是合理的。

这不是：

```text
根据验证集调一个 magic coefficient
```

也不是：

```text
手工给 HCMI 乘 0.5
```

更不是：

```text
增加额外 loss 强行约束
```

只是把模块输出送到更符合其任务定位的路径。

# 14. 如果结果还是持平怎么办

如果修改后仍然出现：

```text
Q ≈ 0.852 ~ 0.854
A ≈ 0.711 ~ 0.713
```

则停止继续调模型。

原因：

- 当前 Full 已经是 best joint；
- Alignment gain 明确；
- Quality loss 只有约 0.004；
- 继续针对验证集追 0.002~0.003 很容易变成过度调参；
- 当前结果本身已经构成合理的 Pareto trade-off。

此时论文中直接写：

> DG-MPQ achieves the strongest perceptual-quality performance independently, while HCMI-ViT provides a clear gain in image-text alignment. Their combination yields the best overall dual-task performance with only a marginal quality trade-off.

中文：

> DG-MPQ 单独使用时取得最优的感知质量预测性能，而 HCMI-ViT 能进一步显著提升图文对齐预测能力。两者联合后在仅产生轻微质量性能波动的情况下取得最佳双任务综合表现。

这是完全可以接受的。

# 15. 如果结果变好怎么办

如果 Task-Oriented Routing 后：

```text
Q >= B1
A > B1
```

则直接冻结最终方案。

最终结构写成：

```text
CLIP ViT-B/16
+
Visual LoRA
+
DG-MPQ
+
HCMI-ViT
+
Task-Oriented Routing
+
Dual Heads
```

但论文里不建议把：

```text
Task-Oriented Routing
```

包装成第三个创新模块。

只在方法实现中描述：

> Considering the task-oriented roles of the two branches, the quality predictor uses the DG-MPQ-enhanced visual representation together with the original textual anchor, while the alignment predictor further incorporates the HCMI-enhanced cross-modal representation.

中文：

> 考虑到两个分支不同的任务侧重，质量预测分支使用 DG-MPQ 增强后的视觉表示与原始文本锚点，而对齐预测分支进一步引入 HCMI-ViT 增强后的跨模态表示。

即可。

# 18. 一句话总结

最终改进的核心是：

> 将共享特征融合改为任务导向的信息路由：质量预测使用 DG-MPQ 增强视觉表示与原始文本锚点，避免 HCMI 的对齐残差干扰质量建模；对齐预测则继续联合 DG-MPQ 与 HCMI 的增强表示，从而在不增加任何参数的情况下减轻双任务之间的负迁移。
